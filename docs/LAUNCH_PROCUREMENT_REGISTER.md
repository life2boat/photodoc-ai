#### 2.2.2 Детальный компонентный анализ сайзинга и доказательная база

1. **Профиль оперативной памяти в Runtime (Расчётная оценка):**
   - **Backend (FastAPI / Uvicorn / Starlette / Async / Threads):** Базовое потребление RSS после старта ~45–60 MB RAM. При активном multipart-стриминге (чанками по 64 KB) и работе фонового потока доставки (`delivery worker`) пиковое потребление оценивается в ~80–120 MB RAM.
   - **Frontend (Nginx Alpine):** Отдача скомпилированной статической сборки SPA dist из `/usr/share/nginx/html`: ~15–25 MB RAM.
   - **Host OS (Ubuntu 24.04 LTS minimal):** Ядро, systemd, sshd, networkd, journald: ~250–350 MB RAM.
   - **Docker daemon (dockerd, containerd, docker-proxy):** ~150–200 MB RAM.
   - **Суммарный steady-state runtime footprint (estimate):** **~500–750 MB RAM**. На сервере с 2 GB RAM расчётный запас свободной памяти составляет ~1.25 GB (>60%).

2. **Потребление памяти при сборке Docker-образов и приоритет prebuilt CI образов:**
   - Фронтенд включает Vite 8, Tailwind CSS, React 19, Radix UI и бандлы `face-api.js` (веса нейросетей распознавания лиц).
   - При выполнении `vite build` процесс Node.js кратковременно потребляет от **800 MB до 1.4 GB RAM**.
   - При сборке на сервере с 2 GB RAM суммарный спрос на память (OS + Docker + backend + Node.js) достигает ~1.7–2.0 GB, что без настроенного swap вызывает срабатывание Linux OOM Killer (`Exit 137`).
   - Настройка файла подкачки 2 GB (`/swapfile`) на NVMe SSD снижает дефицит оперативной памяти, но **НЕ гарантирует предотвращение OOM Killer** (при интенсивном выделении страниц возможен I/O thrashing и критическое замедление ядра).
   - **Приоритетное инженерное требование для тарифа 2 GB RAM:**
     - **Строго рекомендуется деплой готовых предсобранных Docker-образов (prebuilt images) из GitHub Actions CI**. Раннеры GitHub Actions обладают 16 GB RAM, образы собираются и тестируются в CI-пайплайне, а целевой Web VPS выполняет только легковесный `docker compose pull`, исключая нагрузку сборщика на хосте.

3. **Конкуренция за процессор (CPU Contention) и статус нагрузочного тестирования:**
   - Потоковая загрузка multipart-файлов чанками по 64 KB является I/O-bound операцией.
   - Вычисление SHA-256 выполняется через C-библиотеку `hashlib` (~0.15 с на 80 MB).
   - Запись транзакций в SQLite WAL занимает 1–2 мс.
   - Фоновая выгрузка в Яндекс.Диск потоковым HTTP PUT упирается в пропускную способность сетевого канала.
   - **Критическое уточнение по доказательной базе:**
     - Утверждение о том, что конфигурация 1 vCPU гарантированно справляется с нагрузкой 10–50 заказов в день, является **теоретической аналитической оценкой (estimate), а не результатом проведённого нагрузочного теста (load test)**.
     - Полноценная проверка отсутствия очередей и микрозадержек (200–500 мс) при одновременных TLS-рукопожатиях, хешировании и отправке писем требует проведения натурного нагрузочного испытания после развёртывания Staging.
   - Конфигурация с 2 vCPU обеспечивает физическое разделение ядер между веб-сервером и фоновым воркером, устраняя конкуренцию.

4. **Расчёт дискового пространства и статус буфера uploads:**
   - Базовая установка Ubuntu 24.04 LTS: ~4.0 GB.
   - Docker daemon, базовые образы (`python:3.11-slim`, `nginx:alpine`): ~2.0 GB.
   - Рабочие образы приложения (backend ~350 MB, frontend ~70 MB, 1 предыдущая rollback-версия): ~1.2 GB.
   - База данных SQLite (`orders.db` + `-wal` + `-shm`): < 50 MB даже на 10 000 заказов.
   - Журналы (systemd-journald с лимитом `SystemMaxUse=500M`, ротация Docker json-file `max-size: 50m`, `max-file: 3`): ~1.0 GB.
   - Файл подкачки (swapfile при необходимости): 2.0 GB.
   - **Буфер клиентских фото (`uploads/`):** благодаря алгоритму P1 Automatic Photo Cleanup файлы удаляются сразу после подтверждения доставки на Яндекс.Диск. Однако гипотеза о том, что объём буфера никогда не превысит 1.0 GB при пиковом наплыве, остаётся **неподтверждённой оценкой (unproven estimate)** до тех пор, пока поведение системы при одновременных конкурентных загрузках, сетевых сбоях и задержках выгрузки не будет подтверждено натурными стресс-тестами.
   - **Итоговая расчётная потребность в диске: ~11.5–12.0 GB.**
   - На накопителе **25–30 GB NVMe** остаётся **13–18 GB свободного места** (>50% расчётного запаса).

5. **Обоснованность оценки риска Linux OOM Killer:**
   - В runtime-режиме стриминг 64 KB чанками снижает пиковую нагрузку на RAM, однако **риск OOM killer не может считаться нулевым без эмпирических измерений** (при одновременных параллельных multipart-запросах или фрагментации памяти под длительной нагрузкой).
   - При сборке на хосте без swap риск OOM критический; наличие swap снижает вероятность сбоя, но не устраняет риск деградации (thrashing). Деплой prebuilt-образов из CI является основным средством защиты.

6. **Гибкость масштабирования (Cloud Vendor Resizing Flexibility):**
   - Timeweb Cloud и Beget заявляют возможность вертикального изменения конфигурации через панель управления в 1 клик. Переход с 1 vCPU / 2 GB RAM на 2 vCPU / 4 GB RAM осуществляется с сохранением статического IP-адреса и дисковых данных.

### 2.4 Robokassa — регистрация и ключи эквайринга
- **Назначение:** Приём оплаты заказов онлайн. Поддержка банковских карт МИР, Visa, Mastercard, платежей через СБП (Система быстрых платежей), Mir Pay.
- **Обязательность:** Обязательно для приёма коммерческих заказов.
- **Технические требования:**
  - Аккаунт: Личный кабинет юрлица, ИП или самозанятого.
  - Технические параметры в кабинете:
    - `ResultURL`: `https://photo1storage.ru/api/payment/robokassa/result` (метод POST).
    - `SuccessURL`: `https://photo1storage.ru/order-status?payment=success`.
    - `FailURL`: `https://photo1storage.ru/order-status?payment=fail`.
    - Алгоритм расчёта подписи: MD5 или SHA256 (в PhotoDoc AI поддерживается и валидируется на бэкенде).
  - Секреты для `.env`: `ROBOKASSA_MERCHANT_LOGIN`, `ROBOKASSA_PASSWORD1`, `ROBOKASSA_PASSWORD2`.
  - Для Staging: флаг `ROBOKASSA_IS_TEST=1` и тестовые пароли (работает без боевого договора).
- **Текущий статус:** `OWNER_CONTRACT_REQUIRED` (в Staging не блокирует тесты, так как используется test mode).

### 2.5 Яндекс.Диск — облачное хранилище лаборатории
- **Назначение:** Выгрузка обработанных фотографий и текстовых описаний заказов (`info.txt`) для персонала фотолаборатории/печатников.
- **Обязательность:** Обязательно.
- **Технические требования:**
  - Production: Рабочий аккаунт лаборатории с достаточной дисковой квотой. Зарегистрированное OAuth-приложение Яндекса с правами `cloud_api:disk.write` и `cloud_api:disk.read`. Сгенерированный OAuth-токен помещается в production `.env` (`YANDEX_DISK_TOKEN`). Корневой каталог: `/PhotoDoc_Orders/`.
  - Staging: Отдельный изолированный аккаунт Яндекса или выделенная тестовая папка `/PhotoDoc_Staging_R4/` (`YANDEX_DISK_ROOT_DIR=PhotoDoc_Staging_R4`). Использование боевого токена или боевой папки строго блокируется preflight-валидатором.
- **Текущий статус:** `MISSING` (Staging OAuth токен не предоставлен владельцем; production токен не настроен).

### 2.6 SMTP Яндекса — транзакционная почта
- **Назначение:** Доставка электронных чеков и подтверждений клиентам, оперативное информирование администратора лаборатории.
- **Обязательность:** Обязательно.
- **Технические требования:**
  - Адрес отправителя: `noreply@photo1storage.ru` или выделенный ящик Яндекс ID.
  - Настройки подключения: хост `smtp.yandex.ru`, порт `465` (SSL/TLS).
  - Безопасность: Обязательно использование пароля приложений (App Password), сформированного в настройках Яндекс ID (не основной пароль от аккаунта).
  - DNS-аутентификация: Корректно настроенные TXT-записи для домена:
    - SPF: `v=spf1 redirect=_spf.yandex.net`
    - DKIM: открытый ключ, предоставленный Яндекс 360
    - DMARC: `v=DMARC1; p=reject; rua=mailto:...`
- **Текущий статус:** `CONFIGURATION_REQUIRED`.

### 2.7 DNS, Let's Encrypt, Мониторинг
- **Назначение:** Обеспечение доступности и отказоустойчивости веб-интерфейса.
- **Обязательность:** Обязательно.
- **Технические требования:**
  - DNS: Управление A-записями (`@` и `www`), направленными на IP нового Web VPS. TTL перед запуском выставляется в 300 секунд (5 минут).
  - TLS: Certbot с автоматическим обновлением по cron (`certbot renew --dry-run`).
  - Uptime-мониторинг: Бесплатный мониторинг доступности внешнего эндпоинта `https://photo1storage.ru/api/health` каждые 5 минут с уведомлениями в Telegram.
- **Текущий статус:** `PENDING_CONFIGURATION` (не помечаются готовыми до реальной настройки на сервере).

### 2.8 Дополнительные платные сервисы (Опционально)
- **SMS-уведомления (SMS.ru / SMS-Центр):** Резервный канал оповещения клиентов, если почта попала в спам. Подключается опционально по мере роста объёма заказов.
- **WAF / Защита от L7 DDoS (StormWall / Selectel Cloud WAF):** На старте базовая защита от перегрузок и спама обеспечивается встроенным модулем `limit_req` в Edge Nginx (burst=20, nodelay). Платный WAF может быть подключен владельцем при необходимости.
- **Текущий статус:** `NOT_PURCHASED` (не требуется на этапе запуска).
