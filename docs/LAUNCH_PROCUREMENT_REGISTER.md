- **Статус доменов:**

- **Технические требования:**
  - Зона: `.ru`.
  - Управление ресурсными записями DNS (A-запись на IP нового Web VPS без изменения существующих DNS-записей других сервисов).

#### 2.2.2 Детальный компонентный анализ сайзинга

1. **Профиль оперативной памяти в Runtime:**
   - **Backend (FastAPI / Uvicorn / Starlette / Async / Threads):** Базовое потребление RSS после старта ~45–60 MB RAM. При активном multipart-стриминге (чанками по 64 KB) и работе фонового потока доставки (`delivery worker`) пиковое потребление не превышает ~80–120 MB RAM.
   - **Frontend (Nginx Alpine):** Отдача скомпилированной статической сборки SPA dist из `/usr/share/nginx/html`: ~15–25 MB RAM.
   - **Host OS (Ubuntu 24.04 LTS minimal):** Ядро, systemd, sshd, networkd, journald: ~250–350 MB RAM.
   - **Docker daemon (dockerd, containerd, docker-proxy):** ~150–200 MB RAM.
   - **Суммарный steady-state runtime footprint:** **~500–750 MB RAM**. На сервере с 2 GB RAM остаётся более 1.25 GB свободной памяти (>60% резерва).

2. **Потребление памяти при сборке Docker-образов (Build-Time Footprint):**
   - Фронтенд собирается многоэтапным `Dockerfile` (`Stage 1: node:20-alpine`, `npm ci`, `npm run build`). В проект входят Vite 8, Tailwind CSS, React 19, Radix UI и бандлы `face-api.js` (веса нейросетей распознавания лиц).
   - При выполнении `vite build` процесс Node.js кратковременно потребляет от **800 MB до 1.4 GB RAM**.
   - При попытке запустить `docker compose build` непосредственно на сервере с 2 GB RAM суммарный спрос на память (OS + Docker + backend + Node.js) достигает ~1.7–2.0 GB, что без настроенного swap вызывает срабатывание Linux OOM Killer (`Exit 137`).
   - **Технические решения для безопасной эксплуатации тарифа 2 GB RAM:**
     - *Решение А (Рекомендуемое):* Деплой предсобранных Docker-образов (prebuilt images) из GitHub Actions CI. Раннеры GitHub Actions обладают 16 GB RAM, образы собираются и тестируются в CI, а сервер лишь выполняет легковесный `docker pull`.
     - *Решение Б (Резервное для локальной сборки):* Настройка файла подкачки 2 GB на быстром NVMe SSD (`fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile && echo '/swapfile none swap sw 0 0' >> /etc/fstab`). Файл подкачки полностью нивелирует пики памяти при компиляции.

3. **Конкуренция за процессор (CPU Contention):**
   - Потоковая загрузка multipart-файлов чанками по 64 KB является I/O-bound операцией и практически не загружает процессор.
   - Вычисление контрольной суммы SHA-256 выполняется на Си через оптимизированную библиотеку `hashlib` и занимает ~0.15 секунды на файл размером 80 MB.
   - Запись транзакций в SQLite WAL занимает 1–2 миллисекунды.
   - Фоновая выгрузка в Яндекс.Диск потоковым HTTP PUT упирается исключительно в пропускную способность сетевого канала.
   - На 1 vCPU при ожидаемом трафике фотолаборатории (10–50 заказов в день, редкие всплески по 2–3 одновременных заказа) процессор справляется без очередей. В редкие секунды одновременного TLS-рукопожатия, хеширования и выгрузки возможен всплеск задержки (jitter) до 200–500 мс.
   - На 2 vCPU планировщик Linux физически изолирует сетевой стек Nginx и Uvicorn от фонового воркера доставки.

4. **Расчёт дискового пространства (Disk Sizing Breakdown):**
   - Базовая установка Ubuntu 24.04 LTS: ~4.0 GB.
   - Docker daemon, базовые образы (`python:3.11-slim`, `nginx:alpine`): ~2.0 GB.
   - Рабочие образы приложения (backend ~350 MB, frontend ~70 MB, 1 предыдущая rollback-версия): ~1.2 GB.
   - База данных SQLite (`orders.db` + `-wal` + `-shm`): < 50 MB даже на 10 000 заказов.
   - Временный буфер клиентских фото (`uploads/`): благодаря внедрённой архитектуре P1 Automatic Photo Cleanup все фотографии удаляются немедленно после подтверждения доставки на Яндекс.Диск. В буфере единовременно находятся только заказы «в обработке» (не более 1.0 GB при пиковом наплыве).
   - Журналы (systemd-journald с лимитом `SystemMaxUse=500M`, ротация Docker json-file `max-size: 50m`, `max-file: 3`): ~1.0 GB.
   - Файл подкачки (для конфигурации с 2 GB RAM): 2.0 GB.
   - **Итоговая потребность в диске: ~11.5–12.0 GB.**
   - На накопителе **25–30 GB NVMe** остаётся **13–18 GB свободного места** (>50% запаса), что исключает риск переполнения диска.

5. **Риск Linux OOM Killer:**
   - В runtime-режиме риск OOM отсутствует: бэкенд на Starlette/FastAPI строго стримит файлы блоками по 64 KB и никогда не загружает тело запроса в оперативную память; размер заказа строго ограничен константой `MAX_ORDER_BYTES = 80 MB`.
   - Единственный сценарий OOM — компиляция фронтенда без настроенного swap-файла.

6. **Гибкость масштабирования (Cloud Vendor Resizing Flexibility):**
   - И Timeweb Cloud, и Beget предоставляют функцию бесшовного вертикального масштабирования в 1 клик через панель управления. При увеличении тарифа с 1 vCPU / 2 GB RAM до 2 vCPU / 4 GB RAM статический IP-адрес сохраняется, переустановка ОС не требуется, простой составляет менее 60 секунд на перезагрузку виртуальной машины.

### 2.3 Независимое резервное хранилище (Offsite Backup)
- **Назначение:** Хранение зашифрованных копий базы данных `orders.db` и каталога оригиналов `uploads/` вне инфраструктуры основного VPS на случай аппаратного сбоя хостинга, форс-мажора или компрометации сервера.
- **Обязательность:** Обязательно для Production-режима (не блокирует предварительные тесты Staging).
- **Технические требования:**
  - Протокол: S3 API (Yandex Object Storage, Selectel S3) или защищённый SFTP storage.
  - Автоматическая ротация: хранение 7 ежедневных, 4 еженедельных и 3 ежемесячных снапшотов.
  - Предварительное сжатие и локальное шифрование (GPG/AES) до передачи в облако.
  - Объём: 10–50 GB на старте.
- **Текущий статус:** `REQUIRED_BEFORE_PRODUCTION`.

### 2.4 Robokassa — регистрация и ключи эквайринга
- **Назначение:** Приём оплаты заказов онлайн. Поддержка банковских карт МИР, Visa, Mastercard, платежей через СБП (Система быстрых платежей), Mir Pay.
- **Обязательность:** Обязательно для приёма коммерческих заказов.
- **Технические требования:**
  - Аккаунт: Личный кабинет юрлица, ИП или самозанятого.
  - Технические параметры в кабинете:
    - `ResultURL`: `https://photo1storage.ru/api/payment/robokassa/result` (метод POST).
    - `SuccessURL`: `https://photo1storage.ru/order-status?payment=success`.
    - `FailURL`: `https://photo1storage.ru/order-status?payment=fail`.
    - Алгоритм расчёта подписи: MD5 или SHA256 (в PhotoDoc AI поддерживается и валидируется на бэкенде).
  - Секреты для `.env`: `ROBOKASSA_MERCHANT_LOGIN`, `ROBOKASSA_PASSWORD1`, `ROBOKASSA_PASSWORD2`.
  - Для Staging: флаг `ROBOKASSA_IS_TEST=1` и тестовые пароли (работает без боевого договора).
- **Текущий статус:** `OWNER_CONTRACT_REQUIRED` (в Staging не блокирует тесты, так как используется test mode).

### 2.5 Яндекс.Диск — облачное хранилище лаборатории
- **Назначение:** Выгрузка обработанных фотографий и текстовых описаний заказов (`info.txt`) для персонала фотолаборатории/печатников.
- **Обязательность:** Обязательно.
- **Технические требования:**
  - Production: Рабочий аккаунт лаборатории с достаточной дисковой квотой. Зарегистрированное OAuth-приложение Яндекса с правами `cloud_api:disk.write` и `cloud_api:disk.read`. Сгенерированный OAuth-токен помещается в production `.env` (`YANDEX_DISK_TOKEN`). Корневой каталог: `/PhotoDoc_Orders/`.
  - Staging: Отдельный изолированный аккаунт Яндекса или выделенная тестовая папка `/PhotoDoc_Staging_R4/` (`YANDEX_DISK_ROOT_DIR=PhotoDoc_Staging_R4`). Использование боевого токена или боевой папки строго блокируется preflight-валидатором.
- **Текущий статус:** `MISSING` (Staging OAuth токен не предоставлен владельцем; production токен не настроен).

### 2.6 SMTP Яндекса — транзакционная почта
- **Назначение:** Доставка электронных чеков и подтверждений клиентам, оперативное информирование администратора лаборатории.
- **Обязательность:** Обязательно.
- **Технические требования:**
  - Адрес отправителя: `noreply@photo1storage.ru` или выделенный ящик Яндекс ID.
  - Настройки подключения: хост `smtp.yandex.ru`, порт `465` (SSL/TLS).
  - Безопасность: Обязательно использование пароля приложений (App Password), сформированного в настройках Яндекс ID (не основной пароль от аккаунта).
  - DNS-аутентификация: Корректно настроенные TXT-записи для домена:
    - SPF: `v=spf1 redirect=_spf.yandex.net`
    - DKIM: открытый ключ, предоставленный Яндекс 360
    - DMARC: `v=DMARC1; p=reject; rua=mailto:...`
- **Текущий статус:** `CONFIGURATION_REQUIRED`.

### 2.7 DNS, Let's Encrypt, Мониторинг
- **Назначение:** Обеспечение доступности и отказоустойчивости веб-интерфейса.
- **Обязательность:** Обязательно.
- **Технические требования:**
  - DNS: Управление A-записями (`@` и `www`), направленными на IP нового Web VPS. TTL перед запуском выставляется в 300 секунд (5 минут).
  - TLS: Certbot с автоматическим обновлением по cron (`certbot renew --dry-run`).
  - Uptime-мониторинг: Бесплатный мониторинг доступности внешнего эндпоинта `https://photo1storage.ru/api/health` каждые 5 минут с уведомлениями в Telegram.
- **Текущий статус:** `PENDING_CONFIGURATION`.

### 2.8 Дополнительные платные сервисы (Опционально)
- **SMS-уведомления (SMS.ru / SMS-Центр):** Резервный канал оповещения клиентов, если почта попала в спам. Подключается опционально по мере роста объёма заказов.
